# Agent Handoff, Phase 1 (Domain and Consent)

Code complete and verified locally against the **deployed** `ChaukannaStack` in `ap-south-1`.
Branch `feat/phase-1-domain-consent`; `feat/phase-2-agent-local` is rebased on top of it, so the
Phase 2 branch contains all of this.

The Phase 1 gate says *on the deployed URL*, and there is no deployed URL yet: nothing is pushed
past Phase 0 and no Amplify app exists. The gate waits only on the owner steps at the bottom.

## What exists

### Infrastructure (`infra/lib/chaukanna-stack.ts`, deployed)
- DynamoDB `chaukanna` + GSI1, S3 artifacts bucket (TLS enforced, lifecycle rules), Cognito pool.
- Cognito **newer managed login** plus a `ManagedLoginBranding` (without it the login page is empty).
  Public PKCE client. Domain prefix is `chaukanna-<stack uuid head>`, so no account id appears in
  login URLs.
- Callback URLs: `http://localhost:3000/api/auth/callback` always, plus `<appUrl>/api/auth/callback`
  from the CDK context key `chaukanna:appUrl` (set it in `infra/cdk.json` once the Amplify URL
  exists, then redeploy).
- Bucket CORS allows the app origins and the `content-type` header only, not `*`. The same
  `chaukanna:appUrl` redeploy that fixes the Cognito callback also adds the Amplify origin here,
  so **consent uploads from the Amplify URL fail until that redeploy happens**. Verified: a
  preflight from `http://localhost:3000` returns 200, from another origin 403.
- Secrets Manager `chaukanna/invite-signing-key`, generated by AWS. Never in the repo.
- `chaukanna-amplify-compute-role`, defined in CDK. Scoped to the table, `consent/*` objects and the
  secret. `infra/test` fails on any wildcard action.
- Outputs go to `infra/cdk-outputs.json` (gitignored). Deploy:
  `cd infra && AWS_PROFILE=chaukanna npx cdk deploy ChaukannaStack --outputs-file cdk-outputs.json`.

### Web (`apps/web`)
- `src/lib/`: all business logic, unit tested with vitest (`npm test`, 58 tests).
  - `auth.ts` verifies Cognito ID tokens with `node:crypto` against the JWKS. No auth library.
    `auth-flow.ts` handles the code exchange.
  - `invite.ts` signed tokens `{m,h,exp}`, 72 h, with sha256 stored on the member row.
    `learner-session.ts` is the learner cookie; its key is derived separately from the invite key.
  - `db/` holds every DynamoDB call, with zod models. `access.ts` is the Phase 1 default-deny access
    rule (Phase 6 replaces it with Verified Permissions).
  - `consent.ts`: presigned upload key `consent/<memberId>/<iso>.<webm|mp4|ogg>`. The iso becomes the
    consent row's sort key, so replays are no-ops.
  - `i18n.ts`: every learner-facing string, in `hi` and `en`.
- Routes: every route from PRD section 11 that Phase 1 needs, plus two extra sub-routes,
  `POST /api/members/[id]/consent/upload-url` and `POST /api/members/[id]/invite` (fresh link after 72 h).
- Screens: `/join/[token]` (consent), `/me`, `/me/window`, `/me/consent` (learner);
  `/app`, `/app/invite`, `/app/members/[id]/window` (guardian).
- `next.config.ts` sets security headers on every response: `Permissions-Policy` denies the camera
  everywhere (product rule 7) and grants the microphone to our own origin, framing is denied,
  `Referrer-Policy: no-referrer` because invite tokens live in the URL path, plus nosniff and HSTS.
  Verified in the browser: `featurePolicy.allowsFeature('camera')` is false, `microphone` is true.

## Decisions worth knowing
- One household per guardian. Its id is `sha256("household:"+sub)[:20]`, which makes create idempotent.
- The invite accept is single use, with a 10 minute double tap window (`ACCEPT_GRACE_SECONDS`).
- The "stop all" button on `/join` accepts the invite first, then pauses, which binds the pause to
  the right member.
- Re-enabling after a pause is a **fresh recorded consent**, never a toggle.
- If the mic prompt is ignored for 12 s, the screen falls back to typed "हाँ". The consent row stores
  `method`.
- `amplify.yml` writes non-secret env vars to `.env.production` (Amplify SSR does not pass console
  vars to runtime) and fails the build if one is missing. `AWS_REGION` comes from the runtime.
  `APP_URL` defaults to `https://<AWS_BRANCH>.<AWS_APP_ID>.amplifyapp.com`, both provided by Amplify,
  so the first build works before anyone knows the app id. Set it explicitly only for a custom domain.

## Verified
Health route, 401 unauthenticated, 403 cross-origin, 410 on a bad or tampered invite, the full learner
flow in a phone viewport (Hindi consent, typed fallback, window picker, kill switch, English switch),
the voice consent path through presigned S3 PUT and HeadObject, idempotent replay, every row correct in
DynamoDB, log lines that carry ids only, the security headers on a live page, the bucket CORS from
an allowed and a foreign origin, and a real browser presigned PUT from the page origin (200).

The compute role cannot be assumed locally (it trusts `amplify.amazonaws.com`), so it was checked with
`aws iam simulate-principal-policy` instead: every action the app performs is allowed
(`GetItem`, `PutItem`, `UpdateItem`, `Query` on the table and GSI1, `DescribeTable`, `PutObject` and
`GetObject` under `consent/`, `GetSecretValue` on the signing key), while `PutObject` under `drill/`
and `DeleteTable` are denied. That is the usual "AccessDenied at runtime, not at build" pitfall closed
before the first deploy.

Not verified: the guardian screens behind Cognito. They need a real sign-up, which needs a password,
so they are the owner's to check. The code path reviewed clean and fails closed to managed login.

## Secrets and PII
- `scripts/check-staged.sh` runs as a pre-commit hook (`git config core.hooksPath .githooks`, once per
  clone) and blocks `docs/`, any real env file, key material, `apps/agent/runs/` recordings, an
  `.env.example` filled with real ids, and any source file `.gitignore` would swallow.
- A scan of the full history on every branch found no access key, account id, pool id, Cognito domain,
  personal email or fal.ai key. Templates keep placeholders; real values live in
  `apps/web/.env.local`, which is gitignored and matches `infra/cdk-outputs.json` exactly.
- `.gitignore` currently has `docs/` and `.claude/` commented out in the working tree (the owner did
  this to make the docs readable). Nothing publishes them while the hook is enabled, but a `git add -A`
  without the hook would. Restore those lines before pushing if you want belt and braces.

## To pass the gate (account owner)
1. Push the branch (the PAT needs `workflow` scope, because the branch history contains the workflow
   files), then merge to `main`.
2. Amplify console, `ap-south-1`: new app from GitHub, `main`, monorepo root `apps/web`. Service role:
   let Amplify create it. **Compute role: `chaukanna-amplify-compute-role`.**
3. Amplify env vars from `infra/cdk-outputs.json`: `TABLE_NAME, ARTIFACTS_BUCKET, USER_POOL_ID,
   USER_POOL_CLIENT_ID, COGNITO_DOMAIN, VOICE_REGION`. Do not add `AWS_REGION`, and `APP_URL` only for
   a custom domain.
4. Put the Amplify URL in `infra/cdk.json` context `"chaukanna:appUrl"`, then redeploy the stack. This
   is what adds the Amplify origin to both the Cognito callback URLs and the bucket CORS.
5. On a real phone: sign up, create household, invite, open the link, consent by voice, set a window.
   Check rows with the query in `docs/phases/PHASE_1_DOMAIN_AND_CONSENT.md`.
